Core concepts

A short tour of the building blocks. Once these are clear, the rest of the platform follows.

Tenants (workspaces)

A tenant is an isolated workspace, usually one organization. All content, schemas, media, members, API keys and audit events belong to exactly one tenant.

  • Single-tenant mode (TENANCY_MODE=single, the default): one organization per installation. Good for most self-hosted setups.
  • Multi-tenant mode (TENANCY_MODE=multi): many organizations share one installation. Platform administrators create tenants, and users can belong to several and switch between them.

Isolation is enforced twice: every query is filtered by tenant in the application, and PostgreSQL row-level security blocks access to other tenants' rows even if a query forgot its filter. Records of another tenant always look like 404 Not found.

Users, members and roles

A user is a person with an email and password. A membership links a user to a tenant with one built-in role:

RoleCan do
ViewerRead content, media and schemas
EditorEverything a viewer can, plus create, edit and delete content and media
AdminEverything an editor can, plus manage schemas, members, API keys, templates and plugins, and read the audit log
OwnerEverything, including workspace settings and managing other owners

A workspace always keeps at least one owner. Only owners can grant or remove the owner role.

Entities and fields

An entity is a content type such as Article or Product. It has:

  • a key used in URLs (article). Keys cannot change after creation;
  • a name and plural name shown in the UI;
  • a title field used to label records in lists and pickers;
  • optional public access settings for the public API;
  • a list of fields.

A field has a key (price), a label, a type, type-specific settings (such as a minimum, or select options) and rules: required, unique, default value, visible in the public API, and the minimum role that may read or write it.

Keys and types are permanent

Field keys and types cannot be changed after creation, so stored values stay consistent. To change a type, create a new field and remove the old one. Every schema change is versioned, and the history is kept.

Records

A record is one item of an entity, such as one product. Records are validated against the entity's fields on every write, both from the Admin Studio and from the API. Each record has:

  • a stable id (UUID), createdAt, updatedAt, createdBy and updatedBy;
  • a version number that increases on every change. Send it when updating to avoid overwriting someone else's edit (optimistic concurrency);
  • soft deletion: deleted records go to the trash, where admins can restore them or delete them permanently.

Relations

A relation field points to records of another entity in the same workspace, such as an article's author. It holds either one record or many. Targets are checked on every write, and the API can return the linked records inline with ?expand=author.

Media

Uploaded files live in the media library. A media field references one or more files, optionally limited to images, videos, audio or documents. Uploads are checked by their actual content, not just their file name.

API keys

Websites, apps and scripts authenticate with API keys. Each key belongs to one workspace and carries scopes such as records:read or metadata:write. The secret is shown only once, and keys can expire and be revoked.

Templates

A template installs a ready-made set of entities and optional sample content. The first template is the Headless CMS. Templates are versioned and can be upgraded without losing your own changes.

Plugins

Plugins are trusted extensions installed on the server by an administrator and enabled per workspace. They react to record changes, for example by setting a publish date automatically. See Templates & plugins.

Audit log

Sensitive operations are recorded: sign-ins, member and API key changes, schema changes, and record create, update and delete. The audit log records which fields changed, never their values.
